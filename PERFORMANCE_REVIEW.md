# Performance Review — PtuchEditor

Замеры, выводы и ранжированные рекомендации. Оптимизация **не применялась**:
всё, что не продиктовано измерениями или найденным багом, зафиксировано как
«решено не оптимизировать» (раздел 8).

## 1. Методика

**Машина и конфигурация**

- MacBookAir10,1 (Apple M1, 8 ядер 4P+4E), 16 ГБ unified memory, macOS 26.6.2,
  от сети не зависит, Low Power Mode выключен.
- Модель: `models/qwen2.5-3b-instruct-q4_k_m.gguf` (~2 ГБ), `n_ctx=4096`,
  `gpuLayers=-1` (все слои на GPU/Metal), `kPromptBatchSize=n_batch=512`,
  `kMaxGeneratedTokens=512`, llama.cpp b11046 (вендор).
- Сборки: Debug (`build/`) и Release (`build-release/`), Ninja. Замеры фаз
  с реальной моделью — только Release.

**Инструменты**

- `QElapsedTimer` на всех фазах бэкенда; фазовые метрики уходят в
  `BackendDiagnostics` и логи `ptuch.llama`.
- `StallWatchdog` (QTimer, PreciseTimer, период 1 мс) — крупнейший разрыв
  цикла событий UI-потока.
- `rssBytes()` через `task_info(MACH_TASK_BASIC_INFO)` — RSS процесса.
- macOS `sample <pid>` — подтверждение места ожидания в CPU/GPU-стеках.
- Тестовый таргет `PerformanceTests` пишет строки `METRIC ...` — все цифры
  ниже снимаются из них.

**Как воспроизвести**

```bash
# всегда-он замеры (UI-пути, моки) — 10 passed, ~9.5 с
./build/PerformanceTests                 # и/или ./build-release/PerformanceTests

# реальная модель — из КОРНЯ проекта (поиск models/)
PTUCH_MODEL_TESTS=1 ./build-release/PerformanceTests \
    realModelPhasesThroughputMemoryAndCancel

grep METRIC <лог>                        # выборка метрик
```

## 3. Путь запроса (таймлайн)

Остановка печати → видимая подсказка (48 токенов, типовой сценарий):

```
стоп печати
  +475…485 мс   debounce (интервал настройки 500 мс; накладные в пределах
                 погрешности меток теста)
  +0.8 мс       сборка запроса: toPlainText(≈0.8 мс на типовых доках)
                 + capture/buildContext (0.2 мкс) + уход в llama-поток
  +9…39 мс      prompt processing (93 токена)
  +2277…2393 мс генерация 48 токенов (20–21 ток/с — потолок модели/железа)
  +0.3 мс       suggestionReady → первый paint overlay
```

Итого «стоп → подсказка на экране» ≈ **2.8 с**, из которых ~2.3 с —
фундаментальная стоимость генерации на данной модели, ~0.5 с — debounce,
< 5 мс — всё остальное в нашем коде.

## 4. Пункты задания — что измерено

### 4.1 Задержка от остановки печати до начала запроса

**475–477 мс** при `debounceMs=500` (Debug и Release). Накладные нашего кода
между срабатыванием таймера и `backend->generate()` — вклад в <1 мс
(см. сборку запроса). Задержка управляется настройкой пользователя.

### 4.2 Время подготовки prompt

- `PromptBuilder::build()`: **2.53 мкс** (Release, ru200 + 4 стиля,
  system 649 симв.), 0.08 мкс на большом ru2000. *Внимание: в приложении
  PromptBuilder сейчас не вызывается — systemPrompt пуст (находка F3).*
- Сборка контекста: `DocumentState::capture` + `buildContext` — **0.21 мкс**;
  доминирует копия документа через `toPlainText()` — **791 мкс на 1 МБ**
  (типовой документ — единицы микросекунд). Полный путь «документ →
  `GenerationRequest`» — **791–793 мкс на 1 МБ**.

### 4.3 Prompt processing (реальная модель)

- Типовой промпт 93 токена: **9–39 мс** (12 замеров подряд, стабильно);
  суммарно по 5 запросам: 465 токенов за 127–141 мс ≈ **3300–3700 ток/с**.
- 25 нормальных запросов за серии прогонов — **ни одного** столбняка.
- Промпт >512 токенов (2+ чанка): первый чанк 512 ток. — 12–44 мс,
  **каждый следующий чанк ≈ 1994–2113 мс** — находка **F1** (раздел 6).

### 4.4 Generation latency и tokens per second

- 48 токенов: **2277–2393 мс** → **20–21 ток/с** (5 запросов подряд,
  разброс ±0.3 с; TPS не деградирует на 10-м запросе).
- Полный цикл запроса: 2309–2426 мс; residual «прочее» (создание сэмплера,
  эмиссия сигналов, `diagnostics`) — 4–7 мс.
- Загрузка модели один раз на процесс: 1542 мс, +2183 МБ RSS.

### 4.5 Отображение ghost suggestion

- `suggestionReady` → первый paint overlay: **271–344 мкс**.
- paint одного кадра ghost-строки (grab): **60–81 мкс**.
- Вывод: путь отрисовки не является узким местом даже на порядок.

### 4.6 Потребление памяти

- Тест-процесс: 52 МБ (до модели) → 2221–2335 МБ (с моделью).
- Серия из 12 запросов (типовые + большие + отмены): **+25 МБ**
  (2235→2261). Одинаково на всех прогонов — похоже на однократный рост
  ggml-буферов под первый большой граф, а не на утечку; ассерт в тесте
  «<64 МБ» (измеренные 25–27 МБ) держит это под наблюдением.
- Приложение `PtuchEditor` (Release, с загруженной моделью): **RSS 2281 МБ**
  (сэмпл ps через 13 с после старта, стабилен). Без модели — 137–161 МБ.
- 30 циклов создания/разрушения `MainWindow`: потоки 1→1, QObject 113→113,
  RSS не растет (−32 КБ … −10 МБ) — фоновых объектов не накапливается.
- Модель пересоздавалась 0 раз на 12 запросов (`loadedSpy == 1`).

### 4.7 Поведение при отмене

| Сценарий | Результат |
|---|---|
| UI-часть (`rejectSuggestion` → Idle), синхронно из UI | **10–22 мкс**, stale-ответы отбрасываются по `requestId` (unit-тест) |
| Чистая отмена во время генерации (сигнал в +600 мс) | **33–35 мс**, `stopReason=cancelled` |
| Отмена во время prefill, норма (промпт ≤512 ток.) | ≤ 1 чанка = 12–44 мс (проверка флага между чанками, архитектурная граница) |
| Отмена во время prefill в F1-состоянии | 1910–1969 мс — ждет непрерываемый `llama_decode` зависшего чанка |
| Отмена при F2-состоянии (предыдущий промпт отменен) | 1478–1503 мс |
| Гранулярность по генерации | флаг проверяется **на каждом токене** (≤512 шагов) |

`stopReason=cancelled` — во всех случаях, ответ не теряется. UI не блокируется
во время отмены (вызов — 10–22 мкс).

## 6. Находки

### F0 — ИСПРАВЛЕНО: невалидная подпись .app-бандла = вечное зависание загрузки модели

**Симптом**: приложение `PtuchEditor` зависало на старте навсегда — модель
не грузилась (RSS 137–161 МБ, CPU 0%, статус-бар на «Загрузке модели»).
Воспроизводилось 4/4 (и прямой запуск бинаря, и `open`).

**Диагностика** (`sample` зависшего процесса):

```
llamaWorker: llama_backend_init → ggml_metal_device_init →
  ggml_metal_library_init → dispatch_group_wait            (ждет compile-блоки)
dispatch-блок: __ggml_metal_library_compile_all_block_invoke →
  -[AGXG13GFamilyDevice newLibraryWithSource:] → MTLCompilerScheduler::buildRequest →
    dispatch_sync → __DISPATCH_WAIT_FOR_QUEUE__            (ждет рабочую очередь)
com.apple.MTLCompilerConnectionQueue:
  MTLSchedulerRequest::generateXPCBlock →
    xpc_connection_send_message_with_reply_sync → mach_msg  (ДЕМОН НЕ ОТВЕЧАЕТ)
```

**Причина**: linker-подпись внутреннего Mach-O не создаёт печати бандла
(`_CodeSignature` отсутствует, `codesign -vv`:
«code has no resources but signature indicates they must be present»).
Для обычного exe (тесты) XPC-валидация клиента проходит, для бандла с
невалидной печатью — `MTLCompilerService` молча не отвечает, и вся цепочка
виснет. Тест-процесс с той же кодовой базой и теми же dylib грузил модель
за 1.5 с — т.е. страдало только приложение.

**Фикс** (применен в `CMakeLists.txt`):

```cmake
if(APPLE)
    add_custom_command(TARGET PtuchEditor POST_BUILD
        COMMAND codesign --force --sign - "$<TARGET_BUNDLE_DIR:PtuchEditor>"
        COMMENT "Ad-hoc codesign PtuchEditor.app")
endif()
```

**Проверка после фикса**: `codesign -vv` — valid в обоих конфигах после
пересборки; модель в приложении загружается (20 metal-библиотек, RSS
2281 МБ).

### F1 — промпт >512 токенов: второй чанк ≈ 2 секунды

**Замер** (METRIC «большой промпт» в тесте, воспроизводимо):

- 852 токена (2 чанка): чанк 1 (512 ток.) — **33 мс**, чанк 2 (340 ток.) —
  **1997 мс** → `prompt processing 852 ток. за 2056 мс`.
- Замер временным трейсом (снят после диагностики): чанк 2 в 8 из 9
  наблюдений занимал **1994–2113 мс**, в 1 — 168 мс.
- Отмена ни при чём: воспроизводится на запросе, который завершается
  штатно, без каких-либо вызовов `cancel()`.
- Место ожидания (стек-сэмпл): `llama_decode → ggml_backend_sched_graph_compute_async
  → [_MTLCommandBuffer waitUntilCompleted]` — ожидание GPU внутри
  llama.cpp b11046 + Metal; наш код между чанками — микросекунды.
- Нормальные запросы (≤512 ток.) за 25 наблюдений — **0 столбняков**.

**Важно для продукта**: payload приложения — до 2000 символов. Русский текст
при ~2.7 симв./токен даёт **570–740 токенов > 512** — то есть пользователь,
печатая глубоко в длинном документе, реально попадает в эту ловушку:
2-секундный prefill и отмена, «залипающая» на ~2 с.

### F2 — отмена мультичанкового промпта «отравляет» следующий запрос

**Замер** (5/5 прогонов):

- после отмены запроса с промптом >512 ток. первый чанк **следующего**
  обычного запроса декодируется **1.3–2.1 с** (норма 9–39 мс);
- после **завершенного** (не отмененного) большого запроса следующий
  запрос быстр (37 мс) — отравления нет;
- после **чистой отмены генерации** следующий запрос быстр (28 мс) —
  отравления нет;
- восстановление: через **один** запрос после отравленного — 386 мс,
  далее норма. Т.е. эффект разовый, ограниченный, но заметный.

Механизм — внутри того же `llama_decode`/KV-состояния после отмены между
чанками; для продукта последствие то же, что F1 (см. рекомендацию R2, которая
закрывает и F2-сценарий).

### F3 — PromptBuilder не подключен: systemPrompt пуст

`MainWindow.cpp:389` и `:588` передают `/*systemPrompt*/ QString()` —
собранный промпт стиля (`PromptBuilder::build()`, 2.53 мкс) в запрос не
попадает, `styleWeights` в payload — 0. Это корректность продукта
(«смешанные стили не влияют на генерацию»), а не производительность, —
но попало в ревью по списку «избыточный/неполный контекст».
Стоимость исправления — 2.5 мкс на запрос.

### F4 — `toPlainText()` на каждый запрос

`SuggestionController::makeContext()` копирует весь документ в `QString`
ради префикса в 2000 символов. Измерено: **791 мкс на 1 МБ документа**
(типовой — <1 мс). Решено: **не оптимизировать сейчас** (раздел 8),
зафиксирован порог возврата — документы в десятки мегабайт.

### F5 — суффикс вычисляется, но не отправляется

`buildContext()` считает суффикс (после курсора), а payload содержит только
префикс. Лишняя работа — микросекунды; зафиксировано, убрать при следующей
правке сборки контекста.

### F6 — +25 МБ RSS после серии запросов

Однократный рост после 12 запросов, включая первый большой граф (512-токен
чанк). Не растет с числом запросов между прогонами. Под наблюдением
(ассерт «<64 МБ», измерено 25–27 МБ однократно); если на 100 запросах
вырастет линейно — искать утечку.

## 7. Рекомендуемые изменения (ранжированы)

**P0 — сделано в рамках ревью**

- **R1. Ad-hoc подпись бандла после сборки** (F0) — без неё приложение
  не грузит модель вообще. Уже в `CMakeLists.txt`, проверено в обоих
  конфигах.

**P1 — продиктовано измерениями, влияет на пользователя**

- **R2. Обрезать prompt до одного чанка (≤512 токенов)** — левая обрезка
  после токенизации в `generateInWorker` (там же уже применяется лимит
  `n_ctx`; токенизатор уже выполнен, стоимость — единицы микросекунд).
  Обоснование: чанк 2+ стоит ~2 с (F1, 8/9 наблюдений), а штатный payload
  (2000 символов RU ≈ 570–740 ток.) пересекает порог 512. Бонус: закрывает
  F2-сценарий (отмена «между чанками» станет невозможна — промпт всегда
  один чанк, отмена prefill ограничена 12–44 мс). Целесообразно вместе с
  замером «сколько контекста реально отбрасывается» в диагностике.
  Альтернатива/дополнение: проверить F1/F2 на актуальной версии llama.cpp
  (upstream-эскалация: воспроизведение — два чанка по 512, M1/Metal,
  стек `waitUntilCompleted`).
- **R3. Подключить PromptBuilder** (`MainWindow.cpp:389`, `:588`) —
  передавать собранный systemPrompt и стили; perf-стоимость 2.53 мкс.
  Проверить, что `systemPrompt` не раздувает payload (build() держит
  инструкцию компактной — тесты prompt_builder это покрывают).

**P2 — малый эффект / профилактика**

- **R4. Убрать расчёт суффикса, пока он не отправляется** (F5) — при
  следующей правке `buildContext()`.
- **R5. Наблюдать RSS** (F6): повторить замер на серии ~100 запросов
  Release-сборкой; линейный рост = повод для heap-trace.
- **R6. `kMaxPromptChars=8192`** в бэкенде unreachable при капе 2000
  символов — при R2 привести к одному источнику истины (токен-лимит),
  чтобы два порога не расходились.

## 8. Решено НЕ оптимизировать (преждевременно, нет измерений-доказательств)

- **`PromptBuilder::build()`** — 2.53 мкс; **`DocumentState`** — 0.21 мкс;
  **overlay paint** — 60–73 мкс; **cancel UI** — 10–22 мкс. Все на 2–5
  порядков ниже UX-порога.
- **`toPlainText()` на каждый запрос** (F4) — 791 мкс на 1 МБ. На
  типовых документах это <1 мс при общем цикле ~2.8 с. Порог возврата:
  документы в десятки МБ или включение в hot-path, который начнет
  дублироваться (например, при подсказке на каждый символ).
- **Связка UI ↔ worker, очереди сигналов** — разрыв цикла событий 12 мс
  при живой генерации не заметно пользователю; менять архитектуру
  (приоритеты потоков и т.п.) без симптомов — нельзя.
- **20–21 ток/с генерации** — потолок модели q4_k_m 3B на M1 в Metal, а не
  наш код: UI не ждет, отмена пошаговая, фазы разложены и измерены.
  Ускорение = другая модель/квантизация — отдельное продуктовое решение,
  не perf-фикс.
- **Отладочные TRACE-логи** по чанкам временно добавлялись для локализации
  F1/F2 и перед финалом сняты — постоянный лог оставлен агрегатный
  (`prompt processing X токенов за Y мс | чанков: Z`), которого достаточно.

## 9. Итог

- UI не блокируется ни на одной фазе (12 мс худший разрыв при живой
